## Context

Quirl's native command, focused data, Lua, and explicit Bash/Zsh front doors
currently enter their engines through unrelated argument and result shapes. The
engines intentionally retain different semantics, but the composition root has
no common place to preserve source identity, reject undeclared authority, carry
cancellation, distinguish byte and value output, or state who owns cleanup.
Plugin, script, and protocol adapters cannot safely compose on a collection of
implicit conventions.

The common boundary must remain passive. Native process execution and job
ownership stay in `quirl-process`, data evaluation stays in `quirl-data`, Lua
policy and VM ownership stay in `quirl-lua`, and interpreter selection stays in
`quirl-cli`. `quirl-contract` continues to own versioned agent and package wire
documents; making it a runtime owner would add catalog knowledge to every
engine and would conflict with ADR 0016.

This decision introduces the minimum contract. It does not define a new parser,
executor, plugin dispatcher, typed Lua ABI, or streaming implementation.

## Failure model and invariants

- **Cancellation before dispatch.** A set cancellation handle rejects planning
  before effect checks can be followed by engine initialization or side
  effects. Cancellation is a `ResourceLimit` `ShellError`, not a synthetic exit
  status.
- **Cancellation during initialization.** Adapters check the shared handle
  immediately before and after fallible engine construction. Lua receives the
  same atomic handle during construction so its instruction hook and injected
  process host cannot diverge from the request.
- **Cancellation during execution.** Native bounded capture, data evaluation,
  Lua hooks and process callbacks, and reference runners observe the same
  handle. An engine remains responsible for terminating and joining work it
  started before returning the cancellation error.
- **Cancellation after partial output.** Inherited or incrementally written
  output cannot be rolled back. A failure remains `Err(ShellError)` and never
  claims a successful status or value; the engine drains or closes owned
  streams and releases children or VM work before returning.
- **Effect denial.** A plan is created only when every declared effect is in the
  request's allowed set. Denial happens before engine initialization, file
  access, process creation, working-directory mutation, or output writes.
- **Source identity and spans.** One bounded UTF-8 source value carries a
  bounded logical origin and exact text. Adapters pass its text without joining,
  escaping, or normalization. Half-open spans are accepted only when ordered,
  in range, and on UTF-8 boundaries. Engine diagnostics retain or are repaired
  to that exact source at the composition boundary.
- **Byte/value bridges.** Bytes and structured values are distinct closed
  representations. Construction validates byte totals, value node count,
  aggregate retained string/key bytes, and nesting depth with an explicit stack.
  A bridge fails with `ResourceLimit` before retaining data beyond its declared
  limit. This contract does not make a collecting bridge implicit.
- **Engine failure after partial output.** A returned outcome is successful and
  therefore always has one status and one representation. Engine errors are
  returned only through `ShellError`; diagnostics cannot be used as a second
  error hierarchy. Bounded non-fatal diagnostics may accompany a successful
  outcome.
- **Partial adapter initialization.** The adapter that creates a process tree,
  Lua VM, reader, writer, or worker immediately owns it through RAII. Partial
  initialization unwinds in that adapter and preserves the original error even
  when best-effort cleanup also fails.
- **Cleanup ownership.** A plan records whether the selected engine or the
  output consumer owns retained resources. Current engines own processes, jobs,
  VMs, and live streams. An outcome records only cleanup that has completed or
  bounded engine state deliberately retained by the engine; it never transfers
  a raw child, descriptor, VM, or callback to a caller.
- **Status/error/value consistency.** `Exited(code)` is present only in a
  successful outcome, including a non-zero process status. `Cancelled` is an
  error, not `Exited(130)`, at this cross-engine boundary. A value request cannot
  return captured bytes and a byte request cannot silently stringify a value.
- **Resource cleanup.** `quirl-process` preserves process-group, terminal, child,
  pipe, and job guarantees; `quirl-lua` preserves allocator, instruction,
  deadline, registration, callback, and process-host bounds; `quirl-data`
  preserves pull/collection bounds. The shared layer owns none of those
  resources.
- **Bounded retention.** Source bytes, source-name bytes, argument count and
  bytes, input bytes, value nodes/depth/text, output bytes, and diagnostics all
  have explicit maxima. Validation avoids recursion over caller-controlled
  values and reports configured and observed usage where safe.

## Decision

`quirl-core` owns a new passive execution module containing:

- bounded source identity and UTF-8 spans;
- execution mode, request, validated plan, and cancellation handle;
- fixed declared/allowed effect sets;
- byte and structured-value input/output representations;
- status, bounded diagnostics, cleanup ownership/state, and structured outcome;
- validation helpers and constants defining every retained-data bound.

The structured value moves to this lowest common owner. `quirl-data` re-exports
it under its existing `DataValue` name and remains the owner of live streams,
data envelopes, parsers, adapters, and renderers. This is one value contract,
not a parallel data runtime.

The contract is an in-process Rust API, not a frozen serialized protocol.
Serializable passive values use deny-unknown representations where applicable,
but no protocol version or freeze inventory changes until a protocol front door
adopts them as wire data.

`quirl-cli` owns one execution composition function. It validates a request into
a plan, selects the existing engine exactly once, injects process capability and
cancellation, maps catalog effects into runtime effects, and returns the common
outcome. Native interactive execution may still inherit terminal streams, while
bounded capture, data, Lua, and explicit reference modes return their real byte
or structured-value representation. Unsupported plugin/protocol modes remain
typed modes that fail closed until their owning tasks add dispatch.

Existing public engine APIs remain available as narrow adapters. P01 exact
source handling, P02 process lifecycle and terminal handoff, and P05 Lua policy
and fail-closed capability behavior remain authoritative.

## Consequences

- Front doors share one bounded request/plan/outcome vocabulary without
  pretending bytes, values, inherited terminal I/O, and non-zero status are the
  same thing.
- Effect and cancellation policy has one composition point before dispatch.
- Core gains passive runtime types but no executor, parser, process, Lua, data,
  UI, catalog, or CLI dependency; the ADR 0016 graph is unchanged.
- The initial data adapter may collect only where the existing front door
  already requests an owned value or bounded renderer. P08/P09 remain
  responsible for end-to-end typed streaming.
- The initial Lua adapter carries JSON-compatible structured values only. P10
  remains responsible for the typed Lua ABI.
- Plugin and protocol variants define a fail-closed target but do not add plugin
  dispatch. P11 remains responsible for that integration.
